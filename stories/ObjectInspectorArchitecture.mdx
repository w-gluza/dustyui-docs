# How the object inspector is built

The object inspector shows any JavaScript value as a tree you can open, search and copy from. This page explains how it is put together and why.

## The question

There were two ways to build it:

1. One component that walks a value and draws it.
2. Separate parts: one that understands values, one that is a tree, and a thin component joining them.

It is built the second way. A tree is useful without object inspection, for files or navigation. Understanding a value is useful without a tree, for a one-line preview or a log. Joined together, neither could be reused or tested alone.

## Three layers

| Layer           | What it does                                                               | Knows about                   |
| --------------- | -------------------------------------------------------------------------- | ----------------------------- |
| Describe        | Turns a value into nodes: a label, a kind, a one-line preview and children | JavaScript values only        |
| Tree            | Shows nodes as rows, with keyboard, selection and large-list handling      | Nodes with an id and children |
| ObjectInspector | Describes a value, hands the nodes to Tree and adds search and details     | Both                          |

The dependency runs one way. ObjectInspector imports Tree; Tree never imports ObjectInspector. The describe layer and the tree's own logic are plain TypeScript with no React, so a different renderer could use them unchanged.

### Describe

`describeValue(value)` returns one node. Nothing else is read until a row needs it.

It makes three promises:

- **It never throws.** A value that refuses to be read becomes a row that says so, and its siblings still show.
- **It never runs your code on purpose.** Getters are shown as `(...)` and not called. Custom text conversion and custom iteration are ignored.
- **It never follows a loop.** A value that contains itself is shown once, then marked as circular with the path it points back to.

It does not promise to be fast for every value. The precise guarantee is this:

> Collapsed previews inspect a bounded number of entries. Expansion loads children in batches. Property enumeration and proxy traps may still be expensive or execute application code.

#### What each state reads

| State of a row       | What is read                                                                   |
| -------------------- | ------------------------------------------------------------------------------ |
| Closed               | The type, the length or size, and at most five leading entries for the preview |
| Opened               | At most 100 children, or at most 100 ranges                                    |
| A range, when opened | The 100 children in it, or at most 100 smaller ranges                          |
| Scrolled out of view | Nothing; only rows near the view are drawn                                     |

A closed three-million-item array shows `Uint8Array(3000000) [0, 0, 0, 0, 0, …]` and costs the same as a hundred-item one. Opening an array of arrays reads nothing inside the inner arrays beyond those previews.

#### Ranges

A value with more than 100 children shows them in ranges, such as "Items 100 to 199", with ranges inside ranges for very long lists. A range is created only when the row above it is opened, so a list of millions never creates thousands of range rows up front, and every item can be reached.

Ranges are for navigation only. Search looks at real values and never matches a range. Copying writes real values and never a range. An item keeps the same id and the same path however its list is grouped; ranges have ids of their own.

#### What differs by type

| Type                    | How children are read                                                            | Cost to know about                                                                                                   |
| ----------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Arrays and typed arrays | Directly by index, so any range opens at the same cost                           | Named properties of a list longer than 100,000 sit behind a "Properties" row, because finding them lists every index |
| Maps and sets           | By iteration, which has no way to jump                                           | Reading forwards is cheap; opening a range near the end, or going backwards, iterates from the start                 |
| Objects                 | All own keys are listed once, the first time the object is opened, and then kept | JavaScript cannot list keys in pages, so the first opening of an object with millions of keys is slow                |

A closed object shows `{…}` and an arrow without its keys being listed. If it turns out to be empty when opened, the arrow goes. The same holds for anything that might carry properties, such as an empty array or a date.

Until a "Properties" row has been opened, a search says it searched in part, and a copy says it is partial.

Types are recognised by asking the value itself, not by checking its prototype. A Map from another frame is still a Map, and an object that only inherits from Map is not.

A proxy can still run its own traps when it is read, even for a closed row: the type, the length and the first five entries are all read through it. The inspector cannot prevent that, but a throwing trap cannot break it.

### Tree

All the behaviour lives in pure functions: which rows are visible, what a key press does, where focus goes when a row disappears. The React component holds state and draws rows.

It follows the WAI-ARIA tree pattern. The whole tree is one tab stop, arrow keys move between rows, and every row tells assistive technology its level, its position and whether it is open.

Above 200 visible rows the tree draws only the rows near the view and keeps the full scrolling height. The focused row is always kept, so the keyboard position survives scrolling away. Each row still reports its true position in the whole list to assistive technology.

### ObjectInspector

This layer is small. It describes the value, tells Tree how to draw a row, and adds two optional parts:

- **Search** looks through keys and values, counts the matches and opens the way to each one.
- **Details** shows the path, type and whole value of the selected row, and copies either.

Rows are identified by their path. When the value is replaced with new data of the same shape, the same rows stay open.

The value is read as it is when a row is opened. Rows already read are kept and are not read again if the value is changed in place.

## Row ids

Row ids are public, because you pass them in `expanded`, `defaultExpanded` and `selected`. There are two kinds, with different promises.

| Kind     | Example                | Promise                                                                                                                           |
| -------- | ---------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Value id | `$/.animals/[123]`     | Stable. It depends only on where the value sits in the data, never on how its list is grouped into ranges                         |
| Range id | `$/.animals/~i100-199` | Not durable. It names a navigation group and changes when the size of the list or the size of the groups changes. Do not store it |

Build ids with the exported helpers instead of writing the strings:

```ts
import {
  describeValue,
  getChildId,
  getNodeTrail,
  getRangeId,
  ROOT_ID,
} from "dustyui";

const animals = getChildId(ROOT_ID, { type: "property", key: "animals" });
const puma = getChildId(animals, { type: "index", index: 123 });
const range = getRangeId(animals, "items", 100, 200);

const rowsToOpen = getNodeTrail(describeValue(data), puma).map(
  (node) => node.id,
);
```

`getRangeId` takes the first position and the one after the last. `getNodeTrail` returns every row from the root down to a value, ranges included, so it is the simplest way to open the path to a value in a long list. `getPropertiesId` gives the id of the "Properties" row of a very long list.

The path shown in the details panel and copied by "Copy path" is separate from the id. It describes the data, such as `$.animals[123]`, and never mentions a range.

## Decisions and their cost

| Decision                                                   | Why                                                                      | Cost                                                                                        |
| ---------------------------------------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| Getters are never run                                      | Reading a value must not change it or fail                               | You cannot see a getter's result                                                            |
| Only own properties are listed                             | Predictable and fast                                                     | Inherited getters and methods are not shown                                                 |
| Plain objects take a fast path when their type is detected | The first search of a large value was about nine times slower without it | A Map whose prototype was replaced with the plain object prototype shows as an empty object |
| Search stops after 500,000 values                          | A search needs a fixed budget                                            | Larger values are searched in part, and the count says so                                   |
| Long lists are shown in ranges of 100                      | Opening a row must not create a row for every item                       | One or more extra levels to open before reaching an item                                    |
| Object keys are listed only when the object is opened      | A closed row must stay cheap                                             | A closed object shows `{…}`, not its first properties, and its arrow may go once opened     |
| Copy writes readable text, up to 5,000 values              | Valid JSON cannot hold a Map, a BigInt or a circular reference           | The copied text is not guaranteed to parse as JSON                                          |
| Rows in a large tree have one height                       | Positions can be calculated without measuring every row                  | Rows cannot wrap onto a second line                                                         |

## How it is tested

- **Examples** for each kind of value and each key press.
- **Generated data.** Thousands of random values and random key sequences check rules that must always hold: describing never throws, ids are unique, focus is always on a visible row.
- **Hostile values.** Proxies that refuse to be read, revoked proxies, throwing getters and values from another frame.
- **A real browser** for focus, selection, scrolling and screen reader announcements.
- **Deliberate breakage.** After a test is written, the code it covers is broken on purpose to confirm the test fails.

## What was measured

| What                                                                           | Result                |
| ------------------------------------------------------------------------------ | --------------------- |
| Preview of a closed typed array of 3,000,000 items                             | Under 1 millisecond   |
| Opening an array of 1,000 arrays of 100,000 items, with a preview for each row | About 30 milliseconds |
| Reaching the last item of an array of 3,000,000                                | About 5 milliseconds  |
| Reaching the last item of a set of 1,000,000                                   | About 0.1 seconds     |
| First search across 100,000 objects (400,000 values)                           | About 0.3 seconds     |
| The same search again                                                          | About 0.05 seconds    |

## A content security policy that forbids inline styles

One script packs the library, installs it in a fresh Next.js app and checks it in a browser under this policy:

`default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self'`

| Scenario                                                                                     | Result                                                              |
| -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| The package installs, type-checks and builds in the app                                      | Passes                                                              |
| Theme tokens and component styles load, with and without script                              | Passes                                                              |
| Tree rows are in the server HTML before any script runs                                      | Passes                                                              |
| Server-rendered tree, once interactive: indentation, large-list handling, search and details | Passes                                                              |
| Tree mounted in the browser after load: indentation and large-list handling                  | Passes                                                              |
| Components mounted in the browser trigger no policy violations                               | Passes                                                              |
| Server-rendered tree before script runs: indentation                                         | Blocked by the policy; rows show flat until the page is interactive |
| Server-rendered Avatar with a named size (small, medium, large)                              | Passes                                                              |
| Server-rendered Avatar with a size given as a number                                         | Blocked by the policy; it stays at the default size                 |

The policy blocks a `style` attribute rendered on the server. The tree therefore also sets indentation and row spacing from script once the page is interactive. Avatar has no script of its own, so it cannot do the same; its named sizes come from classes and are not affected.

## What is not built yet

- Expand all, collapse all and expand to a level.
- Showing only the rows that match a search.
- A row for inherited getters and methods.
- Swapped arrow keys for right-to-left languages.
- Text in languages other than English for search and details.
